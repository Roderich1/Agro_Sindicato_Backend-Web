## Decisión de formato

F02 adopta UUID v4 canónico generado mediante CSPRNG por interoperabilidad, entropía y soporte
multiplataforma. Es una decisión de detalle F02, no un requisito histórico F01. No se usa IMEI,
Android ID, serial, MAC, advertising ID, número telefónico ni fingerprint. El valor no es secreto y
no concede autenticación, autorización ni ownership.

Mobile conserva el UUID raw. Central almacena sólo:

```text
SHA-256(canonical-lowercase-uuid-v4)
```

El hash permite comparación determinista sin persistir el identificador raw. Tampoco es autoridad de
seguridad. Si un Account tiene múltiples memberships futuras, cada asociación permanece explícita por
`tenantId + memberId`; F02-B no inventa selección multi-tenant ni reasignación automática.

## Lifecycle y responsabilidades

| Etapa | Estado | Responsable |
|---|---|---|
| create | `IMPLEMENTED` | Mobile genera UUID v4 con `Random.secure()` |
| persist | `IMPLEMENTED` | Mobile guarda en Android `noBackupFilesDir` |
| register | `CONTRACT_READY` | Central `POST /auth/clients` después de JWT |
| associate | `IMPLEMENTED` | Central deriva User/Tenant del JWT y resuelve Member activo |
| re-register | `IMPLEMENTED` | mismo client activo devuelve la misma registration y actualiza `lastSeenAt` |
| revoke | `IMPLEMENTED` | Central marca `REVOKED`; repetición es idempotente |
| rotate | `IMPLEMENTED_LOCAL` | Mobile genera UUID nuevo; register + revoke son requests separados |
| device loss | `CONTRACT_READY` | otro client autenticado puede listar/revocar; sesión se delega a #13 |
| reinstall | `IMPLEMENTED_BY_STORAGE_BOUNDARY` | no-backup + desinstalación producen identidad nueva |
| session propagation | `DELEGATED` | Backend #13 |
| Sync verification/switch | `DELEGATED` | F05; legacy continúa sin cambios |
| physical device verification | `NOT_MEASURED` | plan en Mobile PR #61 |

Una registration `REVOKED` nunca se reactiva por re-registro. La continuidad exige un UUID nuevo. No se
afirma atomicidad entre rotación Mobile y los dos requests futuros de register/revoke.

## Backend implementado

`ClientRegistration` contiene `id`, `tenantId`, `memberId`, `clientIdHash`, `status`, `createdAt`,
`lastSeenAt` y `revokedAt`, con relaciones a Tenant y Member. La unicidad es
`(tenantId, memberId, clientIdHash)` y existen índices `(tenantId, memberId)` y
`(tenantId, memberId, status)`.

Endpoints autenticados:

- `POST /api/v1/auth/clients` acepta exclusivamente `{ clientId: UUIDv4 }`.
- `GET /api/v1/auth/clients` lista sólo la membership autenticada.
- `POST /api/v1/auth/clients/:id/revoke` revoca sólo un registro propio.

El body no acepta `tenantId`, `userId`, `memberId` ni `role`. Member y Tenant deben estar activos. Las
respuestas no contienen raw clientId ni hash. Una colisión concurrente converge mediante constraint y
reintento a una sola registration lógica.

## Mobile implementado

`InstallationClientIdStore` crea, lee y rota el UUID. En Android obtiene `noBackupFilesDir` mediante un
MethodChannel mínimo. La app crea el valor al iniciar, no lo imprime y no lo transmite.

- `CLIENT_ID_NOT_IN_SQLITE`: no existe tabla/campo y el archivo vive fuera de la ruta DB.
- `APP_BACKUP_EXCLUDED`: el export contiene sólo `manifest.json`, `database.db` y attachments previstos;
  el test real confirma que restore no reemplaza la identidad actual.
- `ANDROID_SYSTEM_BACKUP_EXCLUDED`: Android usa `noBackupFilesDir`, excluido del backup del sistema.
- Otras plataformas: exclusión de backup `NOT_MEASURED`; el target físico vigente es Android.
- Networking/API client: `ABSENT`.
- Archivos de voz y PR Mobile #8: `UNCHANGED`.

Una identidad corrupta produce `InstallationClientIdCorruptException` y no se sustituye silenciosamente.
