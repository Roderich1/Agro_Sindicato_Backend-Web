## Baseline auth V1

Se preservan `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` y
`GET /auth/me`. El access V1 conserva `sub`, `email`, `role` y `tenantId`. El refresh V1
continúa opaco, hasheado con SHA-256 y ligado a `User`/`tenantId`.

La prueba PostgreSQL real ejecutó login y refresh V1 después de la migración: `PASS`. Sus filas
quedaron `contractVersion=1`, `sessionId=NULL`. Un refresh V2 enviado al endpoint/use case V1 fue
rechazado sin `revokeAllByUser`; un reuse V1 revocó sólo filas `contractVersion=1` y dejó la sesión
V2 del mismo Account activa.

## Diseño Session y schema

`AuthSession` se ancla en `Member`; no duplica `userId` ni `tenantId`:

- `id`, `memberId`, `clientRegistrationId?`;
- `status`: `ACTIVE`, `REVOKED`, `COMPROMISED`;
- `refreshTransport`: `COOKIE`, `BODY`;
- `createdAt`, `lastSeenAt`, `expiresAt`, `revokedAt?`, `compromisedAt?`;
- `ipAddress?`, `userAgent?`.

Relaciones: `Member.sessions`, `ClientRegistration.sessions` y
`AuthSession.refreshTokens`. `Person = ABSENT`.

`RefreshToken` añade `sessionId?`, `contractVersion` con default determinista `1` y
`consumedAt?`. V2 siempre escribe `contractVersion=2` y un `sessionId`; no almacena el refresh raw.

## Contratos V1/V2

V2 añade:

- `POST /api/v1/auth/v2/login`;
- `POST /api/v1/auth/v2/refresh`;
- `POST /api/v1/auth/v2/logout`;
- `GET /api/v1/auth/v2/me`;
- `POST /api/v1/auth/v2/session/client`.

V1 no redirige a V2. Cada refresh endpoint exige su `contractVersion`; el cruce V1↔V2 se rechaza
sin mutación cross-version. Los DTO y decorators Swagger documentan versión, transporte, cookie,
Bearer, errores 401/409 y binding. La validación/diff OpenAPI integral permanece `DELEGATED` a #14.

## Claims y contexto vigente

El access V2 contiene `sub`, `email`, `tenantId`, `role`, `memberId`, `sessionId` y `ver=2`.
No contiene refresh, password, clientId raw ni `clientIdHash`. `role` proviene de `Member.role`.

Login y refresh validan `User.isActive`, `Member.isActive` y `Tenant.isActive`. `/auth/v2/me`
consulta el estado actual de Account/User, Member, Tenant, Session y ClientRegistration ligado; una
prueba cambió el rol después de emitir el access y `/me` devolvió el rol vigente, luego rechazó la
membership inactiva: `PASS`.

Durante coexistencia se selecciona `(tenantId=User.tenantId, userId=User.id)`:

`MULTI_MEMBERSHIP_TENANT_SELECTION = NOT_IMPLEMENTED_DURING_COMPATIBILITY`.

## TTL y cookie

- Access default/config: `JWT_EXPIRES_IN=15m`.
- Session/refresh absolute lifetime default/config: `JWT_REFRESH_EXPIRES_IN=7d`.
- Parser único: enteros positivos con `s`, `m`, `h` o `d`; configuración inválida falla al iniciar.
- `.env.example` fue alineado a `15m`/`7d`.
- Cookie V2: `refresh_token_v2`, `HttpOnly`, `SameSite=Strict`, `Secure` por configuración/producción,
  `Path=/api/v1/auth/v2`.
- `maxAge` usa el tiempo real restante de `AuthSession`.

La rotación conserva `RefreshToken.expiresAt = AuthSession.expiresAt`; no existe sesión sliding
infinita. Cookie V1 también deriva su max-age del mismo TTL configurado; con default `7d` conserva
el comportamiento observable previo.

## Transporte y entropía

`COOKIE` es el default Web. `BODY` devuelve/recibe el refresh explícitamente para un cliente Mobile
futuro; no configura cookie. Cookie y body simultáneos responden `400`. Una sesión sólo acepta el
transporte elegido al crearla.

Refresh V2 usa `crypto.randomBytes(32).toString("base64url")`: 256 bits CSPRNG y 43 caracteres.
Sólo persiste `SHA-256(rawRefreshToken)`; tests verifican que raw y hash difieren. El servicio y
controlador no registran el raw en logs, errores o metadata.

## Rotación atómica y concurrencia

Consumo del token actual, creación del único sucesor y actualización de `Session.lastSeenAt` ocurren
en una transacción Prisma. El arbitraje usa un update condicional por
`consumedAt=NULL AND revokedAt=NULL`.

PostgreSQL 16 real ejecutó dos refresh concurrentes con el mismo raw:

- respuestas exitosas: `1`;
- respuestas rechazadas: `1` (`401`, reuse después de reintentar contención transaccional);
- sucesores creados: `1`;
- sesión afectada: `COMPROMISED`;
- sucesor revocado al comprometer la sesión: `PASS`;
- sesión independiente del mismo Account: permaneció `ACTIVE` y pudo refrescar.

`successor_count <= 1 = PASS`.

El intento inicial con aislamiento `SERIALIZABLE` mantuvo el invariante de un sucesor pero el perdedor
terminó en Prisma `P2028` antes de reuse detection. `INITIAL_CONCURRENCY_ATTEMPT = FAIL` para el
comportamiento del perdedor. Se reemplazó por transacción con update condicional y retry acotado;
`FINAL_CONCURRENCY_ATTEMPT = PASS`.

`CONCURRENT_DUPLICATE_REFRESH_POLICY = CONSERVATIVE_SESSION_COMPROMISE`.

El compromiso conservador preserva el invariante de seguridad: un duplicado simultáneo legítimo
puede obligar a iniciar sesión nuevamente para esa sesión concreta. No se cambió esta semántica
durante el review independiente.

## Reuse, revoked token y múltiples sesiones

Un token con `consumedAt` reutilizado marca exclusivamente su `AuthSession` como `COMPROMISED` y
revoca refresh activos con el mismo `sessionId`; V2 nunca llama `revokeAllByUser`. Una sesión distinta
del mismo Account continúa activa: `PASS`.

Un token administrativamente revocado con `consumedAt=NULL` es inválido pero no se clasifica como
robo/reuse y no compromete la sesión: `PASS`.

## Logout

Logout V2 es público respecto del access y se identifica por refresh, por lo que funciona con access
expirado. Es idempotente, revoca la sesión y sus refresh activos, limpia la cookie y no revoca
`ClientRegistration`. Repetición, preservación del client y supervivencia de otra sesión: `PASS`.
Un refresh anterior de la misma sesión puede identificarla para logout; esto es aceptable porque el
alcance sigue siendo exclusivamente esa sesión.

## Client binding y propagación

El binding deriva session/member/tenant del access V2; el body sólo acepta `registrationId`. Exige
Session y ClientRegistration activos y del mismo Member/Tenant. Primer bind y repetición igual:
`PASS`; cross-member/cross-tenant/revoked: `NOT_FOUND`; rebind distinto: `409`.

La revocación existente de ClientRegistration se extendió transaccionalmente: revoca sólo sesiones
`ACTIVE` ligadas y sus refresh V2. Sesiones no ligadas y de otros registros/members no cambian:
`PASS`. #11 no se reabre.
