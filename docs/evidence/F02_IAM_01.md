- Trazabilidad: `URS-SEC-01`, `SRS-IAM-01`, `SRS-IAM-02`, `DEC-F01-01`, `DEC-F01-12`.
- Estrategia: `EXPAND + BACKFILL`; no es `SWITCH` ni `CONTRACT`.

## Diseño implementado

`User` se conserva como Account compatible y mantiene `tenantId`, `role` e `isActive` como
fuente legacy temporal. `Member` representa la pertenencia tenant-scoped con rol y estado
organizacional. Las relaciones de dominio legacy continúan apuntando a `User`.

`Person = NOT_MATERIALIZED`. No existe un caso central aprobado que justifique crearla. No se
añadieron `Person`, relaciones familiares, `ClientRegistration`, session family ni claims JWT.

## Schema y migración

- Modelo nuevo: `Member(id, tenantId, userId, role, isActive, createdAt, updatedAt)`.
- Relaciones: `Member -> Tenant` y `Member -> User`.
- Unicidad: `UNIQUE(tenantId, userId)`.
- Índices: `tenantId`, `userId`, `(tenantId, isActive)`.
- Migración nueva: `20260923033000_f02_add_member`.
- La migración histórica `20260618010000_init_expanded_flow` no fue modificada; su blob permaneció
  `2724d14b7b38de3e001e0e1480e6e22bfc346317`.
- Backfill: la primera membership reutiliza `User.id` como `Member.id`, copia tenant, rol, estado y
  timestamps. Esto sólo hace determinista el backfill; no identifica conceptualmente ambas entidades
  y las memberships futuras conservan IDs propios mediante `uuid()`.
- No hay `DROP`, rename ni eliminación de columnas o relaciones legacy.

## Dual-write y aislamiento

- `createWithMember` crea User y Member dentro de una sola transacción Prisma.
- `updateWithMember` exige la membership `(tenantId, userId)`, actualiza User mediante
  `updateMany({ id, tenantId })` y refleja `role`/`isActive` en Member dentro de la misma transacción.
- Deactivate reutiliza la misma operación transaccional.
- El reset de contraseña conserva su semántica y sólo endurece la mutación para usar `id + tenantId`.
- Requests, responses, controllers, JWT y endpoints auth permanecen compatibles.
- El seed hace upsert de User + Member transaccional e idempotente.

## Verificación de migraciones PostgreSQL

Se utilizó PostgreSQL 16 en el contenedor desechable `agro-f02-member-pg-20260923`, con bases
separadas `f02_fresh` y `f02_upgrade`. No se utilizó producción ni una base persistente del proyecto.

La revalidación final posterior a PR #87 se ejecutó también sobre PostgreSQL 16 desechable, en
`agro-f02-revalidate-pg-20260923`, con bases nuevas `f02_fresh` y `f02_upgrade`.

### Escenario fresh — intento inicial

`INITIAL_ATTEMPT = FAIL` por una condición histórica previa a F02-A. `prisma migrate deploy` falló al comenzar
`20260618010000_init_expanded_flow` porque el archivo versionado contiene un BOM UTF-8 inicial:

- Prisma: `P3018`.
- PostgreSQL: `42601`, syntax error at or near `U+FEFF`.
- La migración F02-A no llegó a ejecutarse en este escenario.
- La migración histórica no se alteró debido a la prohibición expresa de reescribir historia.

F02-A no originó el BOM. El defecto se reparó de forma explícita y separada mediante issue #86 y PR
#87. Esa PR eliminó únicamente `EF BB BF`, demostró igualdad byte-for-byte del SQL restante, verificó
fresh deploy y compatibilidad con el checksum histórico, y se fusionó mediante el merge commit
`d1f3bb327547f63b3edfb4dad5ba31128921098f`.

### Escenario fresh — revalidación final después de PR #87

`PASS` en PostgreSQL 16 desechable y DB completamente vacía:

- `prisma migrate deploy` aplicó la migración inicial reparada y `20260923033000_f02_add_member`.
- `prisma migrate status`: `Database schema is up to date!`.
- `Member`: presente.
- Antes del seed: 0 User y 0 Member.
- Después del seed: 15 User y 15 Member.
- Memberships duplicadas: 0.
- Divergencias de tenant/role/isActive: 0.

### Escenario upgrade

Para aislar el defecto anterior, en la base desechable se ejecutó el SQL histórico sin el marcador BOM
en memoria, se registró esa migración como aplicada y se insertaron Tenant A, User A y User B. Después,
`prisma migrate deploy` aplicó `20260923033000_f02_add_member` correctamente.

Resultado:

user-b|tenant-a|user-b|DIRECTIVA|false

La prueba adicional del seed, ejecutado dos veces sobre la base upgrade, produjo:

## Rollback

- `TESTED`: atomicidad create User + Member ante una falla forzada de Member; no quedó User parcial.
- `TESTED`: antes de cualquier switch, User conservó tenant, rol, estado y todas las relaciones legacy.
- `DOCUMENTED_ONLY`: desactivar el dual-write y volver a código legacy antes de cutover; no requiere
  borrar Member.
- `NOT_MEASURED`: restauración física/down migration, porque Prisma no genera down migrations y no se
  debe borrar Member en una base compartida para simular rollback.

## Riesgos residuales

1. La migración histórica fue reparada explícitamente en PR #87. Una actualización mayor de Prisma debe
   repetir la prueba de compatibilidad con el checksum histórico documentada en
   `INITIAL_MIGRATION_BOM_REPAIR.md`.
2. Member todavía no es autoridad de JWT ni de las lecturas generales; eso corresponde a entregas
   posteriores y la coexistencia depende del dual-write.
3. No se implementaron ClientRegistration, session family, rotación refresh ni hardening general de
   autorización.
4. Las vulnerabilidades reportadas por `npm audit` son deuda de dependencias fuera del alcance F02-A;
   no se ejecutó `npm audit fix`.
