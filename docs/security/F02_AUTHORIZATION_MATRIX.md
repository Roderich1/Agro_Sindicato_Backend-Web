# F02-IAM-04 — matriz actor × recurso × acción

Fecha: 2026-09-24. Autoridad: `URS-SEC-01`, `SRS-IAM-02`, `SRS-PRIV-01` cuando aplica y `DEC-F01-08` con su aclaración posterior. Esta matriz clasifica contratos alcanzables; **no convierte módulos legacy en arquitectura objetivo**. El actor y tenant efectivos proceden del principal revalidado, nunca de claims stale ni de campos de cliente. `User.role` es `LEGACY_COMPATIBILITY_FIELD`; `Member.role` gobierna autorización.

Clases: `TARGET_CENTRAL`, `TARGET_SHARED`, `TARGET_PRIVATE_OWNER`, `LEGACY_TEMPORARY_ACCESS`, `NO_LIVE_TARGET_TEMPORARY`, `DELEGATED_F05_F06_F07`. Ninguna ruta central privada legacy se promueve a `TARGET_PRIVATE_OWNER`: la autoridad privada objetivo pertenece a Mobile. `A` = AGRICULTOR, `D` = DIRECTIVA, `M` = ADMINISTRADOR. `R` = lectura, `W` = mutación, `—` = denegado. Las lecturas cross-owner de D/M señaladas como temporales **no son un derecho target**.

Política de errores: `401` para credencial/contexto vigente inválido (User, Member, Tenant, Session o registro ligado); `403` para rol/acción prohibida; `404` para ID privado/foreign no visible; `400` para campos no permitidos por DTO o input inválido. No se revela qué entidad del contexto causó un `401`.

Campos recibidos: `tenantId`, `actorUserId`, `role` y `memberId` enviados para **suplantar al actor** son `AUTHORITY_FIELD` y se rechazan cuando el DTO no los admite; nunca sustituyen al principal. Excepciones tipadas: `role` en `/users` es la asignación de rol de un **target** por ADMINISTRADOR, no el rol del actor; `actorUserId` en consulta de auditoría es `FILTER_ONLY` para D/M. `ownerUserId` en query es `FILTER_ONLY` para D/M sólo donde la fila permite lectura temporal; para A se ignora y se usa `principal.sub`. Referencias de negocio como `plotId`, `cropId`, `campaignId`, `productId`, `supplierId`, `warehouseId` y `allocations[].userId` son `BUSINESS_REFERENCE`: requieren validación de tenant y relación/ownership antes de operar. Ninguna excepción D/M se infiere del rango del rol: sólo existe si esta matriz la nombra y el código de la ruta la aplica.

El contrato de Sync F05 no cambia aquí: `SyncOperation.clientId` sigue string legacy, `PAYMENT_CREATE` sigue como dependencia `NO_LIVE_TARGET`, y no se liga a ClientRegistration en F02-D. `Person` no se materializa. El retiro de módulos, proyecciones y OpenAPI integral corresponde a #81/F05/F06/F07/#14, no a esta matriz.
## Aclaracion del review independiente (2026-09-24)

En flujos individuales de AGRICULTOR (inventario inicial, entradas, compra individual y Sync que los despacha), `ProductReferenceDto` es `EXISTING_SHARED_REFERENCE_ONLY`: `productId` o `productName` deben resolver un Product activo existente del tenant. Los metadatos enviados no crean ni actualizan el catalogo compartido. En compra individual, `SupplierReferenceDto` es `EXISTING_SHARED_REFERENCE_ONLY`: `supplierId` o `supplierName` deben resolver un Supplier existente del tenant; `phone`/`address` enviados no lo modifican. La compra conjunta D/M conserva temporalmente su resolucion legacy.

`warehouseId` es `BUSINESS_REFERENCE` con tenant y propietario destinatario: para inventario y compra individual exige `ownerUserId=principal.sub`; para compra conjunta exige `ownerUserId=allocation.userId` en cada asignacion. No hay autoridad documental suficiente para tratar `ownerUserId=NULL` como almacen compartido en estos flujos; se rechaza por seguridad. No se crean capacidades Product, Supplier ni Warehouse nuevas.
